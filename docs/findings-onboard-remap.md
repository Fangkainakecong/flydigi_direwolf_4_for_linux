# 板载映射在 USB 报文里的表现

> 日期：2026-11-18
> 数据：`captures/raw_stream.bin`（12 s：M1 / M2 / FN / Turbo 各 3 s）
> 上游依据：`reference/openflydigi/mapping.py`（含 `tools/keyboard-target-probe` 实测结论）

## 结论先说

板载映射发生在**手柄固件里**，主机收到的已经是映射后的结果。因此 Linux 端
**无法区分**“背键”和“它被映射成的那个键”——这是特性而不是缺陷：零延迟、
跨系统、跨游戏，不需要任何 Linux 软件。

但映射目标的种类决定了 Linux 能看到什么：

| 板载映射目标 | Linux 收到 | 需要 daemon？ |
|---|---|---|
| 标准手柄键（A/B/X/Y/LB/RB/L3/R3/十字/Start/Back/Home） | 标准报文里对应位被置起 → xpad → 对应 `BTN_*` | ❌ 不需要 |
| Turbo | 标准位反复通断，看起来像快速连按 | ❌ 不需要 |
| 宏 | 一串标准按键事件，按序出现 | ❌ 不需要 |
| 键盘 / 鼠标（`TARGET_KEYBOARD = 254`） | **什么都没有**（固件主动抑制该键的原始输出） | ✅ 必须自己做注入 |
| 未映射（identity） | 标准报文里没有，只在厂商扩展字节里可见 | ✅ 需要 daemon 才能用 |

## 实测：M1/M2/FN/Turbo 在报文里的位置

`captures/raw_stream.bin` 统计（32 字节报文，`[0] = 0x00`）：

| 按键 | 出现位置 | 编码 |
|---|---|---|
| **M1** | `[3]` | `0x10`，Cloud 上交替出现 0 / 0x10（约 30 ms 一次，不是持续按住） |
| **M2** | `[3]` | `0x20`，同样交替 |
| **FN** | `[20]` | 值 `1`，约 7 Hz 脉冲 |
| **Turbo** | `[20]` | 值 `2`，约 7 Hz 脉冲 |
| 标准按键字节 `[2]` | — | **全程 0x00**，四个键都不在这里 |

两个附带发现：

1. `[3]` 只能是“扩展按键位图”而不是扳机轴——M1/M2 对应值是精确的 2 的幂。
2. M2 按下瞬间（t≈3.55）`[5]` / `[18]` / `[26]` 出现一串 `1..7` 的快速递增，
   像是板上已有 Turbo 或宏在跑（`[18]=0x20` 同时出现）。**若确认 M2 是出厂默认，
   说明默认配置里就带了重复事件**，需要在读 blob 时核对 `m2` 的 turbo 字段。

## 关键陷阱：`TARGET_KEYBOARD` 会“杀死”这个键

上游用 `tools/keyboard-target-probe` 实测（Apex 5）：

- 把 A 键的目标字节设为 **254** → 手柄**完全停止上报** `BTN_SOUTH`
- 把同一个字节设为 **200**（同样未定义）→ 照常上报 A

所以固件认得 254 这个特殊值，并且**主动压掉自己的手柄输出**。它压掉之后
由谁来按键？Windows 上是飞智自己的**内核过滤驱动**（用户态部分在
`KeyboardMouseInjectRunner`）。Linux 上没有任何东西接手 → **这个键是死的**。

更关键的是：**键值根本不在手柄里**。

> “no command factory in the SDK carries a keyboard key id … All the pad ever
> stores is 127 in a stick's centre byte, meaning 'not acting as a stick'”

也就是说，“M2 = 键盘 V”这条信息只存在于 Windows 的主机配置里。读 840 字节
blob 也拿不到它（`MappingConfigParser` 在写 254 的分支上把两个伴随字节清零）。

## 对迁移策略的直接影响

| 做法 | 结果 |
|---|---|
| 在 Windows 里把背键映射成 L3/R3/十字/ABXY | ✅ Linux 直接可用，无需软件，且永久保存在手柄里 |
| 在 Windows 里把背键映射成 Turbo / 宏 | ✅ Linux 直接可用（表现为快速连按 / 按键序列） |
| 在 Windows 里把背键映射成键盘键 | ❌ Linux 下变死键（Windows 靠驱动补按键） |
| 保持未映射，交给 Linux daemon | ✅ daemon 从 `[3]` / `[20]` 读取，自行决定注入什么 |

**推论：**

1. 我们的 daemon 必须自带映射表（yaml），不能指望从手柄里读出键值。
2. 自己的配置要按“语义”重建，不能指望迁移 Windows 的键盘映射。
3. 如果现在有键是死的，在 Windows 里改回 XInput 键或“无映射”即可复活。
